# Backend Requirements & API Adjustments for Faculty Role

This document details the backend requirements, data contract adjustments, and endpoint fixes needed to support the Faculty features as identified in the QA issue document.

---

## 1. Courses: Module & Class Attachments (Support Non-PDF File Types)
- **Issue**: Previously, module/class file attachments were restricted or configured exclusively for PDF files.
- **Requirement**: Allow uploading and storing documents in presentation, word processing, and spreadsheet formats.
- **Supported Formats**:
  - **Presentations**: `.ppt`, `.pptx` (`application/vnd.ms-powerpoint`, `application/vnd.openxmlformats-officedocument.presentationml.presentation`)
  - **Documents**: `.doc`, `.docx` (`application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`)
  - **Spreadsheets / Data**: `.xls`, `.xlsx`, `.csv` (`application/vnd.ms-excel`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `text/csv`)
  - **PDFs**: `.pdf` (`application/pdf`)
- **Endpoints**:
  - File upload service: `POST /upload/cloudinary-file` (or S3/storage handler).
  - Module attachment endpoints: `POST /teacher/courses/:courseId/modules/:moduleId/classes` or file association endpoints.
- **Action Needed**: Remove any backend validation restricting MIME types or file extensions to only PDF. Ensure storage and MIME type headers correctly reflect the uploaded file type.

## 2. Assessments: Add Exam / Create Assessment
### 2.1 "Mixed" Question Format
- **Issue**: Question formats dropdown needs to include "Mixed".
- **Requirement**: Update the validation schema or Enum for `questionFormat` to accept `"mixed"`.
- **Allowed Values**:
  - `"mixed"` *(New)*
  - `"mcq"`
  - `"written"`
  - `"true_false"` / other existing formats
- **Endpoints**:
  - `POST /teacher/courses/:courseId/assessments`
  - `PUT /teacher/courses/:courseId/assessments/:assessmentId`

### 2.2 Assessment File Attachments
- **Requirement**: Allow attaching `.doc`, `.docx`, `.ppt`, `.pptx`, `.xls`, `.xlsx`, `.csv`, `.pdf` when creating or attaching files to assessments. Ensure the payload and storage handlers accept these file types.

## 3. Notices: Sender Name on Student Notifications
- **Issue**: When a student receives a notice notification generated by a Faculty member, the notification displays details and timestamp but lacks the sender's identity.
- **Requirement**: Ensure the notification payload in `GET /notifications` (and socket push notifications) includes the sender's name and role.
- **Expected Payload Format**:
```json
{
  "id": 101,
  "type": "notice",
  "title": "New Notice from Faculty",
  "message": "Final assessment schedule has been published.",
  "createdAt": "2026-09-25T08:30:00.000Z",
  "actor": {
    "id": 12,
    "name": "Dr. Sarah Connor",
    "role": "teacher",
    "profilePicture": "https://..."
  },
  "data": {
    "senderName": "Dr. Sarah Connor",
    "courseId": 45,
    "courseName": "Distributed Systems",
    "noticeId": 89
  }
}
```
- **Frontend Fallbacks**: The frontend checks `actor.name`, `data.senderName`, `data.facultyName`, `data.teacherName`, and `data.sender`. Providing `actor` or `data.senderName` guarantees clean display (`From: <senderName>`).

## 4. Students & Gigs: Private Chat Separation from Community Chat
- **Issue**: When a Faculty member views a student profile or clicks "Contact Me" on a student's public Gig, the app should initiate a 1-to-1 private chat with the student, completely separated from student community chat rooms.
- **Requirements**:
  1. **1-to-1 Chat Creation**: Ensure the conversation creation endpoint (e.g. `POST /chat/conversations` or `POST /messages/direct`) allows a `teacher` user to initiate a direct conversation with a `student` user.
  2. **Gig Author Verification**: In `GET /gigs` and `GET /gigs/:id`, ensure the response returns author information in `author` or `user` containing:
     ```json
     {
       "id": 204,
       "title": "Mobile App UI Design",
       "author": {
         "id": 55,
         "name": "Alex Mercer",
         "role": "student",
         "profilePicture": "https://..."
       }
     }
     ```
     This prevents the system from confusing the viewing faculty member with the gig owner.

## 5. Student Public Profile: Friends List Population
- **Issue**: When viewing a student's public profile (`GET /profile/public/:id`), the friends section was returning empty or missing data.
- **Requirement**: Ensure `friends` or `mutualFriends` are populated in the public profile response:
```json
{
  "id": 55,
  "fullName": "Alex Mercer",
  "friends": [
    {
      "id": 78,
      "username": "john_doe",
      "profile": {
        "fullName": "John Doe",
        "profilePicture": "https://...",
        "university": {
          "name": "State University"
        }
      },
      "mutualCount": 3
    }
  ]
}
```
- If mutual friends are served via a dedicated endpoint, ensure `GET /friends/mutual/:userId` returns this list.

## 6. Faculty Profile & Settings: "Department" Field
- **Issue**: The Faculty settings screen previously displayed "Faculty" row. The requirement is: *"Since we don't have Faculty column, put Department instead."*
- **Requirement**:
  - In `GET /teacher/me` and `GET /teacher/profile/:id`, return the department name in `department` or `departmentName` inside `profile`:
    ```json
    {
      "id": 12,
      "profile": {
        "fullName": "Dr. Sarah Connor",
        "email": "sarah.connor@university.edu",
        "department": "Computer Science & Engineering",
        "departmentId": 4,
        "designation": "Associate Professor"
      }
    }
    ```
  - Frontend already binds to `profile.department` (or `profile.department.name`), with fallback to `profile.faculty`.
